# Feature: arkodex-consumer-improvements

Objective: make `@fsegurai/manifest-generator` simpler and better to use from Arkodex (and similar docs sites). Status: implemented, uncommitted (user commits manually).
Source: Arkodex consumer audit, 2026-11-18 · Locator: `odd/tasks/arkodex-consumer-improvements.md` · Engram mirror: `odd/arkodex-consumer-improvements/tasks` (create when scheduled).

## Specs

Arkodex paths are relative to the Arkodex repository root. Library paths are relative to `packages/manifest-generator/`.

### S1 (proposal) — Types / JSON Schema entry point
- Friction (refined after checking the source): the root entry already exports `NavigationItem`, `SearchEntry` and friends as types (`src/index.ts:855-868`), but the same module imports `node:fs` / `node:path` at top level (`src/index.ts:1-2`) and there is no JSON Schema for `manifest.json` / `search-index.json`. Arkodex re-declares the shape as `DocsManifestItem` (`projects/kit/core/src/manifest.utils.ts:7-11`) instead of depending on a Node package from browser code.
- Proposal: a node-free `@fsegurai/manifest-generator/schema` subpath (types only + JSON Schema files for `manifest.json` and `search-index.json`), added to `package.json` `exports`.
- Arkodex simplification: `import type { NavigationItem } from '@fsegurai/manifest-generator/schema'`; delete `DocsManifestItem`; optional runtime validation in tests.
- Value/effort: medium / low.

### S2 (proposal) — Optional `prev` / `next` per page
- Friction: Arkodex computes adjacent pages itself (`adjacentManifestPages` in `projects/kit/core/src/manifest.utils.ts:90`, used by `src/app/core/services/docs-manifest/docs-manifest.service.ts:84-85`).
- Proposal: an opt-in generation flag that writes `prev` / `next` (`{ label, route }`) on each page item, following the manifest order.
- Arkodex simplification: delete `adjacentManifestPages`.
- Value/effort: low / low.

### S3 (proposal) — Frontmatter aliases or `--ignore-keys`
- Friction: `validate` warns `Unknown frontmatter key "…" — possible typo` for any key outside `ALLOWED_FRONTMATTER_KEYS` (`src/index.ts:609-631,764`), so external sources (e.g. Arkenda notes with `title`, `created`, `updated`) produce a warning per foreign key.
- Proposal: config `frontmatterAliases` (`title` → `label`, `created` → `publishedAt`, `updated` → `updatedAt`) and `ignoreKeys` / `--ignore-keys` for validation.
- Arkodex simplification: Arkenda-sourced docs generate and validate without pre-processing or noise.
- Value/effort: low / low.

### S4 (proposal) — Verify / provide a browser-safe entry point
- Friction: docs playgrounds would like to demo the generator live over in-memory files. Whether 1.1.0 can already do this is being checked separately; the starting observation is that `src/index.ts` imports `node:fs` and `node:path` at top level while also exporting pure helpers (`extractHeadings`, `makeExcerpt`, `formatTitle`, `cleanItem`, …).
- Proposal: verify what works in a browser today; if needed, provide a browser-safe entry (e.g. `@fsegurai/manifest-generator/core`) exposing pure functions over `{ path, content }[]` with no `node:*` imports, and have the Node entry wrap it.
- Arkodex simplification: a live manifest-generator playground sample without a server step.
- Value/effort: medium / medium (pending verification).
